Section 3 — useEffect and data loading

useEffect(() => { loadEncounterDetails() }, [id])
Runs once on mount. If the user navigates from encounter #5 to encounter #6 without unmounting, the id dependency triggers it again.

Inside loadEncounterDetails()

This is an async function — it runs 4 separate API calls in sequence:

Step 1 — setLoading(true) → shows full-page spinner
↓
Step 2 — getEncounterById(Number(id))
Calls GET /api/v1/clinician/encounters/{id} → returns EncounterResponseDto
Result stored in setEncounter(encData)
↓
Step 3 — getPatientById(encData.patientId)
Uses patientId from the encounter to fetch demographics
Calls GET /api/v1/patients/{id} → stores in setPatient(patData)
↓
Step 4 — Parse JSON fields from the encounter
safeParse(encData.vitalsJson) → sets all 8 vitals states
safeParse(encData.notesJson) → sets soapSubjective/Objective/Assessment/Plan
safeParse(encData.diagnosesJson) → sets diagnosesList
(vitals/notes/diagnoses are stored as JSON strings in DB, parsed here into JS objects)
↓
Step 5 — getAllOrders() → GET /api/v1/lab/orders
Returns ALL lab orders, then filters: .filter(o => o.encounterId === Number(id))
Stores result in setRealLabOrders(...)
↓
Step 6 — getAllPrescriptions() → GET /api/v1/prescriptions
Returns ALL prescriptions, then filters: .filter(rx => rx.encounterId === Number(id))
Stores in setPrescriptions(...)
↓
finally: setLoading(false) → hides spinner, page renders

safeParse — the helper used here

The backend stores vitals, SOAP, and diagnoses as JSON strings inside a single text column. safeParse(jsonString) calls JSON.parse() inside a try-catch. If the string is malformed or null, it returns null instead of crashing.

buildPayload — the other key helper

Every save operation (vitals, SOAP, diagnosis) calls buildPayload(overrides). This constructs the full EncounterRequestDto that the PUT endpoint expects — copying all existing fields from the current encounter state, but replacing only the specific field being updated. This way, saving vitals doesn't accidentally wipe out SOAP notes.

Section 4 — Pure helper functions (no API, no state)

getAge(dobString)

Takes the patient's date of birth string like "1992-06-15", computes the difference from today in milliseconds, converts to years. Returns e.g. "33y". Shown in the demographics banner.

formatDateTime(dateStr)

Converts an ISO datetime string to Indian locale format: "21 Jun 2026, 10:30 AM". Uses new Date(dateStr).toLocaleString('en-IN', {...}). Used for startAt, endAt, signedAt, appointment time.

getStatusBadge(status)

Takes "IN_PROGRESS" / "COMPLETED" / "CANCELLED", returns a JSX <span> badge with the right CSS class and label. Shown in the page header next to encounter ID.

handleDiagnosisSearch(val) — the autocomplete engine

Called on every keystroke in the diagnosis input. It sets newDiagnosis to the typed text, then searches ICD10_CODES (the array imported from icd10Codes.ts) by comparing val.toLowerCase() against each code and description. Shows the top 8 matches in diagSuggestions and sets showDiagDropdown = true. No API call — purely client-side search.

selectDiagnosis(item)

Called when the user clicks a suggestion. Sets newDiagnosis to "J06.9 - Acute upper respiratory infection", hides the dropdown, clears any error. No API call — just state updates.

Section 5 — Button click → service call flows

For each button, here is the exact sequence of what happens from click to server and back.

💾 Save Vitals button (Overview tab)

You click "Save Vitals"
→ calls handleSaveVitals()
↓
1. Calls validateVitals({temp, pulse, spo2, rr, weight, height, bpSystolic, bpDiastolic}) from validation.ts
Returns {errors, warnings, isValid}
Sets vitalsErrors state (turns inputs red) and vitalsWarnings state (turns inputs amber)
If !isValid → toast error, STOP here
↓
2. If warnings exist → toast "X vital(s) flagged as abnormal" but continues
↓
3. setActionLoading(true) — disables the button
↓
4. Builds updatedVitalsJson — combines all 8 vitals into one JSON string
e.g. {"bp":"120/80","bpSystolic":"120","bpDiastolic":"80","temp":"37.0",...}
↓
5. buildPayload({vitalsJson: updatedVitalsJson})
Merges with existing encounter data (keeps SOAP/diagnoses unchanged)
↓
6. updateEncounter(encounter.encounterId, payload)
→ encounterService.ts: PUT /api/v1/clinician/encounters/{id}
→ Backend saves, returns updated EncounterResponseDto
↓
7. setEncounter(updated) — syncs local state with DB
toast.success("Patient vitals saved successfully!")
setActionLoading(false)

📝 Save SOAP Note (each field's Save button)

You click "Edit" on Subjective → setEditingSoap('subjective') — shows textarea
You type. You click "Save"
→ calls handleSaveSoapNote('subjective')
↓
1. validateSoapNote(soapSubjective, 'Subjective') from validation.ts
Checks: if text is not empty, must be ≥ 10 chars
If invalid → setSoapError(msg), toast error, STOP
↓
2. Builds updatedNotes = {subjective, objective, assessment, plan} (all 4 fields)
buildPayload({notesJson: JSON.stringify(updatedNotes)})
↓
3. updateEncounter(id, payload)
→ PUT /api/v1/clinician/encounters/{id}
↓
4. setEncounter(updated), setEditingSoap(null) — closes textarea
toast.success("SOAP SUBJECTIVE note saved!")

🔍 Add Diagnosis button

User types in diagnosis box → handleDiagnosisSearch() runs on each keystroke
→ Filters ICD10_CODES array → shows dropdown
User clicks a suggestion → selectDiagnosis(item) fills the input
User clicks "Add Diagnosis"
→ handleAddDiagnosis()
↓
1. validateDiagnosisInput(newDiagnosis) from icd10Codes.ts
Checks regex: must match pattern like J06.9 or be in "CODE - Description" format
If invalid → setDiagError('Invalid format...'), STOP
If duplicate → setDiagError('Already added'), STOP
↓
2. updatedList = [...diagnosesList, newDiagnosis.trim()]
buildPayload({diagnosesJson: JSON.stringify(updatedList)})
updateEncounter(id, payload) → PUT /api/v1/clinician/encounters/{id}
↓
3. setEncounter(updated), setDiagnosesList(updatedList)
setNewDiagnosis('') — clears input, toast.success("Diagnosis added.")

✅ Sign Encounter button

You click "Sign Encounter" → handleComplete()
↓
1. validateForSigning({bpSystolic, bpDiastolic, temp, pulse, subjective, assessment, diagnosesCount})
from validation.ts
Checks 6 required fields. Returns {canSign: bool, missing: string[]}
↓
If !check.canSign:
setSignMissing(check.missing) → populates the "missing items" list
setShowSignModal(true) → opens modal showing the missing fields list
STOP — does not call API yet
↓
If all fields are present:
setSignMissing([]), setShowSignModal(true)
Opens modal with confirmation message (not missing-fields list)
↓
User reads modal, clicks "Confirm & Sign" → confirmSign()

↓
completeEncounter(encounter.encounterId)
→ encounterService.ts: PATCH /api/v1/clinician/encounters/status/{id}

↓
setEncounter(updated) — status changes to COMPLETED
All IN_PROGRESS-only buttons disappear from UI
toast.success("Encounter signed and completed!")

Section 6 — Tabs and JSX render structure

The JSX is one big return (<div>...</div>). It renders these sections top to bottom, always:

1. Page header — Encounter # + status badge + started time
2. Action buttons row — Edit, Add Prescription, Order Lab, Save Draft, Sign, Delete
Only shown if user?.role === 'CLINICIAN' AND encounter.status === 'IN_PROGRESS'
3. Demographics banner — patient avatar, name, MRN, age/gender, physician, insurance, allergies
Clicking avatar or "Patient Profile" → navigate('/patients')
4. Tab bar — 6 tabs, each sets activeTab on click via setActiveTab(tab)
5. Tab content — controlled by activeTab state
Each tab is wrapped in {activeTab === 'X' && (<div>...</div>)}

Overview tab content

Chief Complaint card → displays encounter.chiefComplaint text

Vitals card → shows 7 visual stat boxes (read-only display), then if status is IN_PROGRESS, shows 8 editable inputs + "Save Vitals" button

Encounter Info card → metadata grid: ID, Status, Created By, Signed By, Started At, Ended At

SOAP Notes tab

Renders 4 cards (S, O, A, P) in a loop. Each shows the text. If clinician + IN_PROGRESS, shows Edit button. Clicking Edit sets editingSoap to that key — swaps text display for a textarea + Save/Cancel buttons.

Diagnosis tab

If clinician + IN_PROGRESS: shows search input + autocomplete dropdown + Add button. Always shows the diagnosesList — each entry as a row with ICD code badge + description + optional remove button.

Orders tab

If realLabOrders.length === 0: shows empty state with "Create Lab Order" button (navigates to /lab/new with encounterId in router state). Otherwise renders <LabOrdersTable> passing orders, context="encounter", onCancelOrder callback, actionLoading.

Prescriptions tab

If prescriptions.length === 0: empty state with "Create Prescription" button (navigates to /prescriptions/new). Otherwise a table: medication name, dosage, frequency, duration, and if IN_PROGRESS+CLINICIAN, Edit and Delete icons per row.

Timeline tab

Static display. Builds an array of timeline events from current state — "Encounter Started" (always shows), "Vitals Logged" (if vitals exist), "SOAP Notes Drafted" (if soap exists), "Encounter Signed" (if status=COMPLETED). Filters with .filter(e => e.show) then maps to timeline dot rows.

Early returns before the JSX

If loading === true: returns a full-page spinner div immediately — nothing else renders.

If !encounter (load failed): returns "Encounter not found" + back button.

Only if loading === false AND encounter !== null does the full page render.

Section 7 — The 4 Confirmation Modals

All 4 modals use the same <Modal> component from components/ui/components.tsx. The component takes isOpen, onClose, title, and children. The children are the modal body — buttons + message.

Sign Encounter Modal (showSignModal)

Has two modes depending on signMissing.length:
If missing items exist → shows red warning list of missing fields, only a Close button (cannot sign yet).
If signMissing is empty → shows green confirmation message, "Confirm & Sign" button calls confirmSign() → PATCH API.

Delete Encounter Modal (showDeleteModal)

Shows encounter ID and patient name. "Delete" button calls confirmDelete() → DELETE API → navigate away.

Remove Prescription Modal (showDeleteRxModal)

Simple confirmation. "Remove" calls confirmDeleteRx() which uses pendingDeleteRxId — the rxId saved when you clicked the trash icon on the row.

Cancel Lab Order Modal (showCancelLabModal)

"Cancel Order" calls confirmCancelLabOrder() which uses pendingCancelLabId. After cancel, re-fetches all orders to update the table.

Section 8 — Exactly where and how each file is used

models/types.ts — TypeScript contract layer

EncounterResponseDto — type annotation for the encounter state. Every field access like encounter.patientId, encounter.vitalsJson, encounter.status is TypeScript-safe because this interface defines them. If the backend changes a field name, TypeScript will flag the mismatch at compile time.

PatientResponseDto — same pattern for patient state. Used for patient?.name, patient?.mrn, patient?.dob in the demographics banner.

PrescriptionResponseDto — the type for each item in the prescriptions array. rx.medicationName, rx.dosage, rx.rxId all come from this type.

LabOrderResponseDto — type for each item in realLabOrders. Also passed to <LabOrdersTable orders={realLabOrders}>.

TabType and TAB_ICONS — defined locally in the file, not from types.ts — but follow the same pattern.

encounterService.ts — the encounter API module

Uses raw fetch() (not Axios). Defines its own getAuthHeaders() function that reads the token from localStorage and returns the Authorization header.

getEncounterById(id) — called once in loadEncounterDetails() on page load.

updateEncounter(id, payload) — called 4 times: save vitals, save any SOAP field, add diagnosis, remove diagnosis. It's the workhorse of this page.

completeEncounter(id) — called in confirmSign(). Uses PATCH not PUT.

deleteEncounter(id) — called in confirmDelete(). Returns void.

patientService.ts — uses Axios via the shared api.ts instance

getPatientById(id) — called once in loadEncounterDetails() right after the encounter loads, using encData.patientId. The patient data populates the demographics banner (name, MRN, age, gender, insurance).

Note the architectural difference: patientService uses api.get() from the Axios instance (which has the interceptor auto-adding the token), while encounterService uses raw fetch() with a manually built header. Both work but are inconsistent — a real code review note.

prescriptionService.ts — uses raw fetch like encounterService

getAllPrescriptions() — called in loadEncounterDetails(). Returns ALL prescriptions from the system, then the component filters them: .filter(rx => rx.encounterId === Number(id)). This is client-side filtering — not ideal at scale but fine for this project.

deletePrescription(rxId) — called in confirmDeleteRx(). After delete, the state is updated optimistically: the deleted rx is filtered out of prescriptions without re-fetching from server.

labService.ts — uses Axios via api.ts

getAllOrders() — called in loadEncounterDetails() AND again after confirmCancelLabOrder() to refresh the list. Same client-side filter pattern as prescriptions.

cancelLabOrder(id) — called in confirmCancelLabOrder(). After cancellation, a fresh getAllOrders() call re-fetches to show the updated status. Different pattern from prescriptions (which uses local state filter) — here a full re-fetch is done.

utils/validation.ts

validateVitals() — called inside handleSaveVitals(). Takes an object with 8 string fields. Internally converts each to a number, checks physiological ranges (e.g. temp 30–45°C), checks cross-field logic (diastolic < systolic). Returns {errors, warnings, isValid}. The errors object is stored in vitalsErrors state and used inline in the JSX to turn input borders red.

validateSoapNote(text, field) — called in handleSaveSoapNote(field). Only check: if text is non-empty, must be ≥ 10 chars. Empty is allowed (clinician may not have filled every section).

validateForSigning() — called in handleComplete() before opening the sign modal. Checks 6 things: BP systolic, BP diastolic, temp, pulse, subjective text, assessment text, and at least 1 diagnosis. Returns a list of any missing items. If the list is non-empty, the modal shows the warning instead of the confirmation.

utils/icd10Codes.ts

ICD10_CODES — an array of 40 objects, each with code and description. Used in handleDiagnosisSearch(): the component filters this static array locally on every keystroke. No API call — instant, zero latency autocomplete.

validateDiagnosisInput(value) — uses ICD10_REGEX = /^[A-Z]\d{2}(\.\w{1,4})?$/i. If input is "J06.9 - Acute URI", it splits on " - " and tests the first part "J06.9" against the regex. If it's just a code like "R51", it tests the whole string. Returns true/false. Called in handleAddDiagnosis() before the API call.
